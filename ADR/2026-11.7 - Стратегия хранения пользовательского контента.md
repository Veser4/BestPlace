**ADR: Стратегия хранения пользовательского контента**

**Дата:** 12 ноября 2026 г.

**Статус:** Принято

**Контекст:**

Пользователи BestPlace загружают фотографии мест размером до 10 МБ. Необходимо обеспечить хранение файлов, серверную проверку и доступ с учётом модерации. Решение должно соответствовать микросервисной архитектуре и учитывать рост объёма контента и ограниченные ресурсы проекта. Файлы должны размещаться у российского провайдера в регионе Россия.

**Рассмотренные варианты:**

1. **Файловая система сервера:** Проста на старте, но усложняет совместный доступ к файлам при нескольких экземплярах сервиса.
2. **MySQL, поля BLOB:** Хранение файлов увеличивает размер БД, нагрузку на неё и объём резервных копий.
3. **Объектное хранилище российского провайдера:** Отделяет файлы от реляционных данных и предоставляет API для работы с ними. В качестве конкретного решения рассматривается Yandex Object Storage.

**Решение:**

Использовать **Yandex Object Storage** в регионе **Россия** для фотографий и отдельный сервис **filestorage** на Go для управления ими.

- Файлы хранятся в Yandex Object Storage, а их метаданные в собственной схеме MySQL сервиса filestorage.
- Filestorage принимает изображения, проверяет фактический формат и размер, загружает их в хранилище и возвращает `fileId`. Остальные сервисы сохраняют связи с этим идентификатором.
- Ключи доступа к Yandex Object Storage находятся только у filestorage. Сервис предоставляет API загрузки, удаления и получения файлов. Например, `GET /files/{fileId}` возвращает содержимое файла из хранилища в теле ответа с соответствующим заголовком `Content-Type`.
- При замене фотографии создаётся новый файл. До одобрения изменений пользователям показывается прежняя опубликованная версия.
- При удалении файла из системы он удаляется не сразу, а помечается как deleted. Полное удаление происходит после 3 месяцев.

**Обоснование:**

- Работа с файлами и их проверка сосредоточены в одном сервисе.
- Хранилище и filestorage можно масштабировать отдельно от каталога.
- S3 API позволяет менять реализацию хранилища без изменения интерфейсов остальных сервисов при проверенной совместимости операций.

**Последствия:**

- Потребуется развёртывание и сопровождение дополнительного сервиса и хранилища. Конкретная реализация S3 выбирается с учётом доступных ресурсов.
- Для частично выполненных загрузок и неудачных удалений нужны повторные попытки и очистка лишних файлов. Файлы действующих черновиков, заявок и опубликованных мест сохраняются.
